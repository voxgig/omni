# Code review — omni (2026-08)

A full review of the runner and its 23 ports. omni is a test runner, so a bug
here **hides bugs** in everything it tests — leniency, not crashes, is the
operative risk. Findings were checked against source; those marked *(reproduced)*
were verified by compiling and running the code.

Companion review of the sibling project is in `voxgig/sekreto`
(`doc/design/review-2026-08.md`); the two share a root cause (hand-rolled parsers
without depth limits or a shared edge-case corpus).

## Overall

The core is strong: exact `out` comparison (`deepequal`) rejects every coercion
trap, absent-vs-null is carried by a real ABSENT marker in every port, and all
audited ports carry genuine can-go-red negative tests. The weaknesses are (1) the
`match` partial-matcher, which has several false-pass paths, (2) the hand-rolled
JSON parsers, which diverge between ports and crash on deep input, and (3) the
parity net (`check_parity.py`), which checks names, not behaviour.

## High

### OM-1 — The `match` partial-matcher has several false-pass paths *(reproduced)*
`typescript/src/Runner.ts` `matchval` / `typescript/src/Util.ts` `jsonstr`.

- An absent value stringifies to the literal `"undefined"` (`Util.ts`, `jsonstr`)
  and is then substring-tested, so a **typo'd match key passes**:
  `match:{out:{labell:"fine"}}` against `{label:"x"}` → PASS (`"fine"`, `"un"`,
  `""` are substrings of "undefined"). Converts "field missing" into "matches".
- `__UNDEF__` and `__NULL__` both fold to `null` in `matchval`, then
  `null == base || NULLMARK === base` — so `__UNDEF__` matches present-null and
  `__NULL__` matches absent. This collapses exactly the distinction AGENTS.md says
  never to collapse.
- ~~Empty containers assert nothing: `match:{}` passes any result;
  `match:{out:{}}` passes `12345`.~~ **Reclassified as intended, not a bug.**
  An empty container in a match is a deliberate structural placeholder ("a
  value is here, contents unchecked") — voxgig/struct's corpus relies on it,
  and the `struct-compat` gate requires omni to stay a faithful drop-in for
  struct's runner. An initial fix here was reverted; empty containers remain
  a match-anything placeholder, as in struct.
- String leaves match the *serialized* value, including map **keys** and numbers:
  `match:{out:"even"}` passes `{even:false}`; `match:{out:"5"}` passes `55`;
  `match:{out:""}` passes anything.

Exact `out`/`deepequal` is unaffected; the leniency is confined to `match`. Fix in
canonical, add `spec/fib.json` counter-cases, propagate to all ports.

### OM-2 — Hand-rolled JSON parsers diverge between ports and crash on depth *(reproduced)*
The whole point of omni is that the ports agree; the in-tree parsers don't.
- **C** (`c/src/json.c`) parses numbers with `strtod(text,NULL)` ignoring the end
  pointer → silently wrong values: `[1-2]` → `[1]`, no error. Unique to C.
- **Haskell** accepts trailing commas and resolves duplicate keys first-wins;
  **OCaml** is also first-wins. Canonical (and Rust/C/Lua/Zig) are last-wins.
- All five hand-rolled parsers mishandle surrogate-pair `\uXXXX` escapes, each
  differently.
- No depth limit anywhere: deep nesting → C **segfault**, Rust **abort**, others
  catchable. Canonical throws a catchable `RangeError`.

Fix: align to canonical semantics (last-wins, strict number tokenization, reject
trailing commas, correct surrogate combining) and add depth limits. Zig is exempt
(uses `std.json`).

## Medium

### OM-3 — `check_parity.py` verifies names, not behaviour
`tools/check_parity.py` `defined()` runs `re.findall` over raw source, matching
identifiers inside comments and strings, with zero semantic checking. A port whose
`deepequal` was `return true` passes `make parity`. ~~DOCS.md §9's claim that fib.json
"proves" match-rule parity is overstated.~~

**Half closed, and the halves are different.** The *tool* was never
misrepresenting itself: its docstring already said "this is a NAME check, not a
behaviour check ... a port whose `deepequal` was `return true` would pass here",
and named the gap it leaves — "when those do not exercise an area (ctx, err.name,
number formatting, ...), ports can drift while this check stays green." Verified
by mutation: gutting python's `deepequal` to `return True` leaves
`check_parity.py` green while `make test-python` fails with 4 failures. Making
the name check semantic across 24 languages is not the fix; the corpus is the
mechanism, exactly as the docstring says.

**The DOCS.md §9 overstatement was real and is fixed.** It claimed everything
outside the variance table "is identical across all twenty-three ports, and the
Fibonacci suite proves it on every run". The suite is JSON and cannot prove
anything about a value JSON has no literal for. §9 now states that limit, with
NaN as the worked example.

**What remains open is the coverage hole, not the tool.** No port unit-tests
`deepequal`, `clone`, `getpath`, `walk`, `jsonstr`, `stringify` or `pathify`
directly — every port's suite is the fib corpus runner alone, so the whole util
surface is exercised only incidentally and only through JSON-expressible values.
Closing it needs a decision on mechanism (a `__NAN__`-style sentinel in the spec,
or per-port unit tests); see the note under OM-4.

### OM-4 — Real port divergences fib.json cannot see
All in areas the spec never exercises: ~~Swift `errify` hardcodes `name:"Error"`~~
(fixed - `swift/Sources/Omni/Runner.swift` now returns the thrown type's name via
`errname`, pinned by the `err.name` entry that landed with voxgig/omni#5);
~~Swift/Elixir/Clojure never attach `client` to the `ctx` argument~~ (fixed by the
same PR's `context` group); ~~NaN deep-equality diverges (Python/...)~~ - python
fixed too, by the same PR: `python/voxgig_omni/util.py:114-115` returns true for
two NaNs. ~~**Still open**: NaN deep-equality in **Ruby, PHP and Clojure**~~ — **closed, and
the list was short by three.** A survey of all 23 ports found **six** diverging,
not three: **php, ruby, lua, perl, clojure and zig**. All six are fixed; the
other sixteen already matched canonical.

**#45's own review then found two defects in those fixes, both real.** Fixed in
the follow-up:

- **perl — a regression #45 introduced.** The bare self-inequality test
  (`$a != $a && $b != $b`) also fires for the *strings* `"NaN"` and `"nan"`,
  because Perl's `looks_like_number` accepts both, so two differently spelled
  strings started comparing **equal** — canonical treats them as distinct.
  Measured: `deepequal("NaN","nan")` returned true. **The prior code was
  correct here** (`NaN == NaN` is false, so it returned unequal), which makes
  this squarely a regression rather than an incomplete fix. Now guarded on the
  string forms matching too: two genuinely computed NaNs both stringify to
  `"NaN"`, so real NaN equality survives while string distinctness returns.
- **clojure — an incomplete fix.** The `double?` guard rejects `Float/NaN`,
  which this port's `number?`-based `isnum` accepts, so two Float NaNs still
  compared unequal. NaN-ness is now tested after `(double ...)` coercion, the
  way `numstr` already does it.

Both are the same shape as everything else here: the first fix was checked
against the case that motivated it and not against the cases around it.

Each fix matches the port's own existing idiom — php and ruby and lua and perl
verified by direct execution here, clojure and zig by source reading plus CI
(neither toolchain exists in the authoring environment, and this note does not
claim otherwise).

**Ruby was the sharpest, and nearly escaped a second time.** It returns `true`
for `deepequal(Float::NAN, Float::NAN)` — but only because `Float::NAN` is a
single constant object caught by the `a.equal?(b)` identity fast-path at the top
of the function. Two *distinct* NaNs (`0.0/0.0` vs `INFINITY-INFINITY`) returned
`false`. A test written the obvious way passes and proves nothing; the survey
carried a distinct `DIVERGES_VIA_IDENTITY_ONLY` verdict precisely for this shape.

**The fix is currently invisible to every test in the repo**, which is OM-3's
point restated: `spec/fib.json` has no NaN and cannot have one (JSON has no NaN
literal; the sentinel set is `__NULL__`/`__UNDEF__`/`__EXISTS__` only), and no
port unit-tests `deepequal` at all. So all six ports could regress silently
tomorrow. **Choosing the coverage mechanism is a live decision**: a `__NAN__`
sentinel would make the area corpus-reachable for every port but is a spec change
touching the exported API surface, `fixjson`, the match rules and all 23 ports;
per-port unit tests are far smaller and arguably the right home, since NaN is
outside what a JSON corpus can express by definition.

Still open from this finding: Go flag coercion is internally inconsistent;
error-capture scope is narrower in Go/Java/Swift/Elixir/Clojure.

voxgig/omni#5 - the `err.name` entry and the `context` group are what pin the two
fixes above.

### OM-5 — Regex: catastrophic backtracking; count-overflow crashes
All in-tree engines are the same un-memoized CPS backtracker (Lua **62 s** for 22
chars). Zig `{n}` parsing overflows `usize` → Debug panic; OCaml's `{n}` raises a
`Failure` that escapes its handler. C's POSIX bridge silently drops `(?:...)`.

## Low / informational
Empty `set` passes vacuously; error matching is message-substring only; `__proto__`
in a spec evaporates in `clone` (safe, but the clone loses the key → vacuous match);
non-plain objects collapse to `{}`; C drops NUL; number leniency (`+5`,`01`,`.5`) is
accepted by all hand-rolled parsers (mutually consistent).

## Confirmed strengths
- `deepequal` (exact `out`) is excellent: `5≠"5"`, `true≠1`, `[]≠{}`, extra keys
  rejected, `null≠undefined`, NaN handled.
- Absent-vs-null carried by a real ABSENT marker in every audited port.
- The four required negative tests genuinely go red in all audited ports.
- Go/Python/Ruby/PHP/Java runners are line-for-line faithful to canonical.
- Spec parsing uses strict `JSON.parse`; the runner rethrows its own `OmniError`
  as a failure, so it can't fake an `err` pass.
